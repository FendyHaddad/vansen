# Server-driven catalog and mobile contract correctness — design

Date: 2026-09-23. Status: approved in conversation, awaiting spec review.
Repos: backend + web `~/IdeaProjects/vansen`, mobile `~/StudioProjects/vansen-mobile`.

Sub-project 1 of 4 in mobile parity. The others, each with its own spec:
2. personas on mobile; 3. cloud upscale, styles and trends; 4. version history,
job cancel, ledger, password recovery. The mobile release-readiness plan
(`vansen-mobile/docs/superpowers/plans/2026-09-17-mobile-release-readiness-review-and-implementation-plan.md`)
keeps its hardening tasks (MT-01 purchase verification, MT-02, MT-04, MT-05,
MT-08, MT-09). This spec absorbs MT-03, MT-07 and the storefront part of MT-01.

## 1. Problem

A model's definition — versions, sizes, ratios, qualities, prices — is compiled
into each app. The web and backend share `model-families.ts` (synced to
`_shared/` by `npm run sync-shared`). Mobile keeps a hand-written Dart copy,
`lib/data/catalog/model_families.dart`, that has drifted:

- GPT Image offers versions 1 / 1.5 / 2 (default 2); the backend only accepts
  `2.5-flare` / `2.5-sunburst` → 400 `invalid_settings` on the default request.
- FLUX is marked reference-capable (backend `imageInput: false` → 400
  `reference_unsupported`) and offers 4MP at every ratio (backend: 1:1 only).
- Displayed prices ignore the prompt allowance, per-reference cost and the Nano
  Pro thinking allowance: Nano Pro 1K shows 23, charges 27; GPT medium shows 9,
  charges 3 (13 with a reference).
- Sora, stale Runway/Seedance/Kling options; missing Seedream/FLUX versions.

Separately, mobile is wrong against the live contract in ways unrelated to the
catalog: blank library tiles (`mediaUrl` is empty when a thumbnail exists),
first page only, client-rebuilt variations of items the server cannot vary,
video items rendered as images, canceled-but-paid subscribers blocked, and an
uncommitted `x-vansen-client` header that makes iOS Stripe checkout return
403 `lane_not_allowed`.

## 2. Principle

One source of truth for what a model is and costs: `model-families.ts`. One
on/off switch: `public.models.enabled`. The backend serves both; every app
renders what it is served and decides no business rule itself. Adding or
retiring a model, version or option value, or changing a price, is an edit to
`model-families.ts` plus `./deploy.sh` — no App Store release.

The catalog stays in code, not a table: a price change stays reviewed, tested
and versioned in git.

## 3. `GET /catalog`

Public, unauthenticated, like `/capabilities`. Route in a new
`supabase/functions/api/catalog.ts`, registered from `app.ts`. Payload built by a
pure function `buildCatalog(families, enabledRows, …)` in `_shared/catalog/`
(generated by `sync-shared` like the rest of the shared catalog).

```jsonc
{
  "catalogVersion": "2026-09-23.2",
  "families": [
    {
      "id": "nano-banana",
      "label": "Nano Banana",
      "provider": "Google",
      "kind": "image",               // image | video
      "enabled": true,               // models.enabled
      "plan": "studio",              // minimum plan to use it
      "maxReferences": 1,            // 0 = no reference input
      "maskInput": false,
      "axes": [                      // render order
        { "id": "version", "control": "choice",
          "values": [{ "value": "pro", "label": "Pro", "tooltip": "…", "tag": "Latest" }] },
        { "id": "aspectRatio", "control": "aspectRatio", "values": [{ "value": "1:1" }] },
        { "id": "resolution", "control": "choice", "values": [ … ] }
      ],
      "defaults": { "version": "pro", "aspectRatio": "1:1", "resolution": "1k", "batch": 1 },
      "batch": { "min": 1, "max": 4 },
      "combos": [                    // every valid setting combination
        { "settings": { "version": "pro", "aspectRatio": "1:1", "resolution": "1k" },
          "credits": [27, 29] }      // index = reference count, 0..maxReferences
      ]
    }
  ],
  "flat": {                          // fixed-price items
    "editTools": [{ "id": "edit-remove", "label": "Remove", "credits": 10, "enabled": true }],
    "upscale": { "credits": 7, "enabled": true },
    "persona": { "creditsPerImage": 46, "enabled": false }
  },
  "styles": [ … ],                   // style-presets.ts: id, label
  "trends": [ … ],                   // trend-presets.ts: id, label, family, settings
  "toolPlans": { "cutout": "pro", "crop": "studio" }   // entitlements.ts
}
```

Decisions:

- **`combos` is both the validity table and the price table.** A client derives
  which values of each axis are selectable by filtering `combos` against the
  values already chosen, so version→resolution, version→quality and
  ratio→resolution exclusions need no rule language. `credits[n]` is the price
  of ONE output with `n` references, computed by the existing `creditCost()`;
  the server rounds up per output, so the price is not linear in references
  and must be tabulated. A batch costs `credits[n] × batch`: the gateway creates
  one item per batch slot, each priced at the unit price (`app.ts` ~2628-2635).
- **Only live families are listed.** A decommissioned family, version or value
  is absent; clients show only what is listed.
- **Control types are a closed set:** `choice`, `aspectRatio`, `toggle`,
  `duration`. A client that meets an unknown `control` hides that family and
  shows "Update the app to use this model". It never submits a setting the user
  could not see.
- **Plans and packs are not in the catalog.** Prices live in Stripe and the App
  Store.
- **Styles, trends and tool plans are included now** (data only) so sub-project
  3 and the mobile tool locks read the same source; their mobile UI is out of
  scope here.
- **Caching:** `ETag: "<catalogVersion>-<hash of enabled flags>"`,
  `Cache-Control: public, max-age=300`. `If-None-Match` → 304.

## 4. Backend changes

1. `_shared/catalog/build-catalog.ts`: `buildCatalog()` — pure, unit-tested.
2. `api/catalog.ts`: the route; reads `models (id, enabled)`.
3. `POST /generations` accepts optional `catalogVersion`. When it is present,
   differs from `CATALOG_VERSION`, and the settings fail validation, respond
   409 `catalog_stale` ("The model options changed. Pick again.") instead of
   400 `invalid_settings`. Same for `reference_unsupported`. Valid settings from
   an old version are served normally.
4. `GET /profile` → `subscription.entitled: boolean`, computed by the gateway's
   existing `activePlan` rule (`active`, or `canceled` with
   `current_period_end > now()`). One rule, read by both apps.
5. Retire `contracts/catalog/` and `scripts/export-catalog.mjs` (and their
   verify gate); `/catalog` replaces them. Add `npm run catalog:mobile`, which
   writes the current `buildCatalog()` output (all families enabled as in the
   migrations' seed) to a path given as an argument, for mobile's bundled copy.

All additive: live clients are unaffected.

## 5. Web changes

- The subscription gate reads `subscription.entitled` instead of checking the
  status itself.
- The web keeps importing `model-families.ts` directly; web and backend deploy
  together from one commit. A guard spec asserts that `buildCatalog()` lists
  exactly the families, axes and values the composer offers, so the two views of
  the same file cannot diverge.

## 6. Mobile changes

Riverpod + dio + path_provider, following the repo's CLAUDE.md (TDD, no
comments, no nested ifs, i18n keys ≤ 3 words, `Log.error` on unexpected
failures).

**Catalog**
- `lib/data/catalog/catalog.dart`: `Catalog`, `CatalogFamily`, `CatalogAxis`,
  `ControlType { choice, aspectRatio, toggle, duration, unknown }`,
  `valuesFor(family, axis, chosen)`, `priceFor(familyId, settings,
  referenceCount)` → `int?` (null blocks Generate).
- `lib/data/catalog/catalog_repo.dart`: bundled `assets/catalog/catalog.json`
  → disk cache → `GET /catalog` with `If-None-Match`. Refresh at start, on app
  resume, and after `catalog_stale` or `model_disabled`.
- `catalogProvider`: serves cached/bundled at once, swaps in the fresh copy.
- Delete `lib/data/catalog/model_families.dart` and its test; the model picker,
  option controls, price label, `generate_gate.dart` credit check, edit-tool
  prices and tool locks all read the catalog. One `OptionControl` widget maps a
  control type to the existing widgets. Requests send `catalogVersion`.
- Catalog labels are English. `ms.json` covers app chrome only (D4 English-only
  launch decision is open).

**Contract fixes**
- Paid access: `generate_gate.dart` reads `subscription.entitled`.
- Library (MT-07): read `thumbUrl`; fetch `GET /generations/:id` for full media
  on detail, save, share and edit; page with `limit` / `cursor` / `nextCursor`.
- Replay: variation and retry call `POST /generations/:id/variation` and
  `/retry`; buttons shown only when `GET /generations/:id/retryable` says so.
  The client-side request rebuild in `generate_controller.dart` goes.
- Video and persona items render as poster + badge, open a read-only detail;
  no edit, no client variation.
- Errors: one `ApiError` → message + action mapping for every gateway code the
  app can receive, including `model_disabled`, `catalog_stale`,
  `studio_required`, `pro_required`, `subscription_required`,
  `account_suspended`, `rate_limited`, `too_many_jobs`, `daily_cap`,
  `content_policy`, `invalid_settings`, `reference_unsupported`,
  `purchase_rejected`, `retry_later`. Keep the 5xx `errorId`.
- Uncommitted WIP (crash reporting, `client_tag.dart`, `x-vansen-client`): kept.
  On iOS it lands only together with `x-vansen-storefront` from StoreKit's
  current storefront country (never device locale); `GET /billing/lane` is
  called with the same value. The global error hooks keep Flutter's default
  logging (they currently return `true` and swallow it).

## 7. Testing

- Backend (Deno): every `combos[].credits[n]` equals `creditCost(family,
  settings, {hasReference: n > 0, referenceCount: n})`; every combo passes the
  gateway's settings validation and every non-listed combination fails it;
  disabled family → `enabled: false`; ETag → 304; `catalog_stale` for an old
  version with invalid settings and none for valid ones; `entitled` for active,
  canceled-in-period and canceled-past.
- Web: the composer/catalog guard spec; gate spec reading `entitled`.
- Mobile (`flutter test --no-pub`, test first): bundled catalog parses;
  `valuesFor` and `priceFor`; unknown control hides the family; repo fallback
  network → cache → bundled and 304 handling; every error code mapped; gate
  reads `entitled`; paging and `thumbUrl`; replay routes and `/retryable`;
  storefront header on iOS requests.
- `npm run verify` green in the backend repo; `flutter analyze` and
  `flutter test` green in mobile.

## 8. Rollout

1. Backend + web in one `./deploy.sh` (additive). Read back `/catalog` and
   `/profile` in production.
2. Mobile: code change, then a TestFlight build. Store submission stays with
   the owner and remains blocked on the release-readiness items.

## 9. Out of scope

Personas, cloud upscale, styles/trends UI, version history, job cancel,
ledger, password recovery (sub-projects 2–4); video generation (D7); purchase
verification and other MT hardening tasks.
